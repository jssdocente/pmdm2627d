# **3.6 Laboratorio de Prácticas y Codelabs**

El laboratorio de la UT3 es, como el de la UT2, **una sola app Android que crece codelab a codelab**. Parte de la plantilla del curso con el menú del laboratorio y, en siete codelabs guiados, añade las piezas de una app moderna: un tema propio de Material 3, listas, la estructura de `Scaffold`, formularios, navegación con Navigation 3, un ViewModel y recursos traducidos. Después, tres **retos autónomos** te piden construir juegos completos con todo lo aprendido.

El laboratorio se divide en dos bloques:

1. **Codelabs guiados:** paso a paso, con la teoría, el código completo y un tag de Git con la solución.

2. **Retos autónomos:** un enunciado con requisitos que resuelves por tu cuenta.

### 1.1. Descargarlo con Git (recomendado)

```bash
git clone https://github.com/jssdocente/pmdm2627-lab-ut3.git lab-ut3
cd lab-ut3
git checkout c3.01-inicio      # el punto de partida del primer codelab
git switch -c mi-lab           # tu rama para trabajar
```

Abre la carpeta `lab-ut3` en IntelliJ IDEA (*File › Open…*, la carpeta que contiene `settings.gradle.kts`). La configuración del SDK y del JDK es la misma que la de la plantilla; si algo falla, consulta su README.

Trabaja siempre en **tu rama**. Así, para cada codelab tienes dos opciones:

- **Seguir con tu código:** si terminaste el codelab anterior, continúa en tu rama.
- **Partir de la solución:** si te quedaste a medias, crea una rama nueva desde el tag de inicio: `git switch -c mi-lab-3.03 c3.03-inicio`.

Para comparar tu trabajo con la solución de un codelab:

```bash
git diff c3.03-fin            # qué te falta o qué has hecho distinto
```

!!! tip "Tags nuevos"
    Si las soluciones de los retos se publican después de que clonaras el repositorio, descárgalas con `git fetch --tags`.

### 1.2. Sin Git

En la página del repositorio, en **Tags**, cada tag se descarga como `.zip`. Descomprímelo en una ruta corta y sin acentos (por ejemplo `C:\PMDM\lab-ut3`), igual que la plantilla. Para el codelab siguiente, descarga su tag de inicio o sigue trabajando sobre tu carpeta.

**Para añadir una pantalla** al laboratorio (lo harás en cada codelab):

1. Añade una entrada a `enum class PantallaLab` en `LabApp.kt`, con su título y su descripción.

2. Añade su rama al `when` de `LabApp`, envuelta en `PantallaConVolver`.

El menú no se toca: recorre `PantallaLab.entries` y la nueva tarjeta aparece sola.

!!! info "`consumeWindowInsets` en `MainActivity`"
    Las pantallas del laboratorio van dentro del `Scaffold` de `MainActivity`. Desde el Codelab 3.03, muchas tienen además su propio `Scaffold`. `MainActivity` aplica `consumeWindowInsets(innerPadding)` para que los `Scaffold` de dentro sepan que el hueco de las barras del sistema ya está cubierto y no lo repitan.

#### 1. La Interfaz

1. **Indicador de vidas.**

    - Un `LinearProgressIndicator` con las vidas que quedan y el texto `"Vidas restantes: 4 / 6"`.
    - Su color cambia según quedan menos vidas (por ejemplo, `primary`, `tertiary` y `error`).

2. **Palabra oculta.** Una casilla por letra: las descubiertas muestran su letra y el resto quedan vacías.

3. **Teclado virtual.**

    - Un `FilledTonalButton` por letra del abecedario, incluida la Ñ.
    - Las letras ya probadas se deshabilitan (`enabled = false`), igual que todo el teclado al terminar la partida.

4. **Fin de partida.** Un `AlertDialog` aparece solo al ganar o perder, informa del resultado (y de la palabra, si se pierde) y ofrece **Jugar de nuevo**.

#### 2. Requisitos Técnicos Obligatorios

- `AhorcadoUiState`: una `data class` con lo que muestra la pantalla, ya preparado (la palabra enmascarada, las vidas, las letras probadas como `Set<Char>` y el estado de la partida).
- `AhorcadoViewModel` con `MutableStateFlow` privado y `StateFlow` público, que usa las funciones del dominio. Recibe la lista de palabras por el constructor, con un valor por defecto.
- `AhorcadoContent` sin estado, dividido en componentes (`VidasIndicator`, `PalabraOculta`, `TecladoVirtual`…), y `AhorcadoScreen` con `viewModel()` y `collectAsStateWithLifecycle()`.
- Un **test de interfaz** en `src/androidTest`: con un ViewModel creado con la palabra `"KOTLIN"`, pulsar la Z muestra `"Vidas restantes: 5 / 6"` y deja la Z deshabilitada. Repasa [3C.4 §5 Probar las pantallas Compose](./c-arquitectura/3c.4-testing.md#5-probar-las-pantallas-compose).

### Reto 3.02 · Wordle

- **Tag de inicio:** `r3.02-inicio` · **Solución:** `r3.02-solucion`
- **Paquete:** `retos/reto02_wordle`

Adivina una palabra de cinco letras en seis intentos. Tras cada intento, cada casilla se colorea con una pista.

<div style="display: flex; flex-direction: row; justify-content: center; align-items: flex-start; gap: 1.5rem; flex-wrap: wrap; margin: 1.8rem 0;" markdown="1">

<figure style="margin: 0; text-align: center; max-width: 260px;" markdown="1">

![El Wordle tras dos intentos](./codelabs/images/r3.02-wordle.png){ style="border-radius: 8px; box-shadow: 0 4px 10px rgba(0,0,0,0.15); width: 100%; max-width: 250px;" }

<figcaption style="font-size: 0.85rem; margin-top: 0.5rem; color: var(--md-default-fg-color--light);"><strong>Figura 4:</strong> Una solución posible, tras dos intentos.</figcaption>
</figure>

</div>

#### 1. La Interfaz y las Reglas

1. **El tablero.** Seis filas de cinco casillas (`Column` de `Row`). Cada casilla es una `Surface` con bordes redondeados y la letra en negrita.

2. **Las pistas.** Al enviar un intento, cada casilla toma un color del tema:

    - **Acierto** (letra en su sitio): `primaryContainer`.
    - **Presente** (la letra está, pero en otra posición): `tertiaryContainer`.
    - **Ausente** (la letra no está): `surfaceVariant`.

3. **Letras repetidas.** Una letra solo da tantas pistas como veces aparece en la palabra secreta: si la secreta tiene una R y el intento dos, solo una puede ser *presente*.

4. **El teclado.** Las letras en filas, más **Borrar** y **Enviar**. Cada tecla se pinta con la mejor pista conseguida con su letra.

5. **Mensajes y final.** Enviar una palabra de menos de cinco letras muestra un aviso y no gasta intento. Al acertar o agotar los seis intentos, un `AlertDialog` muestra la palabra y ofrece jugar de nuevo.

#### 2. Requisitos Técnicos Obligatorios

- El cálculo de las pistas es una **función pura** del dominio, sin Compose: `evaluar(secreta: String, intento: String): List<Pista>`.
- **Tests unitarios** de `evaluar`, incluido un caso con letras repetidas, y al menos uno del ViewModel.
- `WordleUiState` inmutable y `WordleViewModel` con los eventos `escribirLetra`, `borrar`, `enviar` y `reiniciar`.
- `WordleContent` sin estado, con al menos una `@Preview` a mitad de partida.

### Reto 3.03 · Memory

- **Tag de inicio:** `r3.03-inicio` · **Solución:** no se publica
- **Paquete:** `retos/reto03_memory`

El clásico juego de parejas: dieciséis cartas boca abajo, ocho parejas. Este reto no tiene solución publicada.

#### 1. La Interfaz y las Reglas

1. **El tablero.** Una cuadrícula de 4 × 4 con **`LazyVerticalGrid(columns = GridCells.Fixed(4))`** y `key` en cada carta.

2. **Las cartas.**

    - Cada carta es una `ElevatedCard` táctil.
    - Boca abajo muestra un reverso uniforme con el color `primary`. Boca arriba, su símbolo (un emoji o un icono).
    - Las parejas encontradas se quedan a la vista.

3. **El turno.**

    - La primera carta se da la vuelta. Con la segunda se suma un intento y se comparan.
    - Si son pareja, se quedan boca arriba. Si no, se muestran un momento y se vuelven a ocultar.
    - Mientras dos cartas distintas están a la vista, no se puede pulsar ninguna otra.

4. **Marcador y final.** Arriba, el número de intentos y un botón para reiniciar la partida con las cartas barajadas de nuevo. Al encontrar todas las parejas, un `AlertDialog` muestra los intentos.

#### 2. Requisitos Técnicos Obligatorios

- `MemoryUiState` inmutable y `MemoryViewModel` con las reglas. Las cartas se barajan con `shuffled()`.
- La espera antes de ocultar dos cartas se hace en el ViewModel con una corrutina: `viewModelScope.launch { delay(…) }`. Nunca con `Thread.sleep`, que congela la interfaz.
- La pantalla no tiene estado propio del juego: solo pinta el `UiState` y avisa de cada pulsación.

## 5. Lista de Verificación de Calidad (*Checklist*)

Antes de entregar, comprueba en cada pantalla:

- [ ] **Tema:** ningún color escrito a mano; todo sale de `MaterialTheme.colorScheme`, y la pantalla se ve bien en modo oscuro.
- [ ] **`Scaffold`:** el contenido aplica `innerPadding` y nada queda debajo de las barras.
- [ ] **Listas:** todas las `LazyColumn` y `LazyVerticalGrid` usan `key` con un id único.
- [ ] **Arquitectura:** los juegos guardan el estado y las reglas en un ViewModel con `StateFlow`; la pantalla no tiene variables de juego sueltas.
- [ ] **Giro:** la partida sobrevive al girar el móvil.
- [ ] **Tests:** `./gradlew test` y `./gradlew connectedAndroidTest` terminan en verde.
