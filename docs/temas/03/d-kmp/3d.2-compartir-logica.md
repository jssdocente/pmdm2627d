# **3D.2 Compartir la lógica en `commonMain`**

En [3D.1](./3d.1-anatomia-proyecto-kmp.md) creamos un proyecto Kotlin Multiplatform y vimos cómo se organiza. Ahora vamos a llevar a él la app de juegos de 3C: **el dominio, los datos, los ViewModel y la configuración de Koin**. Las pantallas las compartiremos en [3D.3](./3d.3-compose-multiplatform.md).

Vas a comprobar algo muy satisfactorio: gracias a la arquitectura de [3C.2](../c-arquitectura/3c.2-clean-architecture.md), la mayor parte del código **se mueve sin cambiar ni una línea**. Separar las capas y mantener el dominio en Kotlin puro tenía precisamente este objetivo.

Al terminar sabrás:

- Qué partes de la app van a `commonMain` y qué librerías necesitan.
- Usar ViewModel y Koin desde el código común.
- Resolver lo que cada plataforma hace de forma distinta, eligiendo entre `expect`/`actual` y una **interfaz inyectada con Koin**.
- Ejecutar los tests en `commonTest`, una sola vez para todas las plataformas.

---

## 1. El plan: qué va a cada sitio

| Pieza (de 3C) | Destino | ¿Cambia? |
|---|---|---|
| `Juego`, `JuegoRepositorio`, casos de uso | `shared/src/commonMain` | No |
| `JuegoRepositorioEnMemoria` | `shared/src/commonMain` | No |
| `CatalogoViewModel`, `DetalleViewModel` y sus `UiState` | `shared/src/commonMain` | No |
| Módulos de Koin e `initKoin()` | `shared/src/commonMain` | Mínimo: se separa la parte de Android |
| Tests de casos de uso y ViewModel | `shared/src/commonTest` | Pequeños cambios en las anotaciones |
| Pantallas Compose | De momento en `androidApp`; en 3D.3, a `commonMain` | — |
| `MainActivity` y la clase `Application` | `androidApp` | No |

Al terminar este apartado, la app Android funcionará igual que antes, pero toda su lógica vivirá en `shared`, lista para que la app de escritorio la use.

---

## 2. Dependencias del código común

En `shared/build.gradle.kts`, añade al source set `commonMain` las librerías multiplataforma que necesita la lógica, y al source set `commonTest`, las de los tests:

    kotlinx-coroutines-test = { module = "org.jetbrains.kotlinx:kotlinx-coroutines-test", version.ref = "kotlinx-coroutines" }
    jetbrains-lifecycle-viewmodel = { module = "org.jetbrains.androidx.lifecycle:lifecycle-viewmodel", version.ref = "jetbrains-lifecycle" }

=== "shared/build.gradle.kts"

    ```kotlin
    kotlin {
        // … targets de 3D.1 …

        sourceSets {
            commonMain.dependencies {
                // … las de Compose que ya tenías …
                implementation(libs.kotlinx.coroutines.core)
                implementation(libs.jetbrains.lifecycle.viewmodel)   // ViewModel y viewModelScope
                implementation(libs.koin.core)
                implementation(libs.koin.compose.viewmodel)          // koinViewModel() y viewModelOf
            }
            commonTest.dependencies {
                implementation(libs.kotlin.test)
                implementation(libs.kotlinx.coroutines.test)
                implementation(libs.turbine)
            }
            androidMain.dependencies {
                implementation(libs.koin.android)                    // androidContext() en el módulo de plataforma
            }
            jvmTest.dependencies {
                implementation(libs.koin.test)                       // verify() solo funciona en la JVM
            }
        }
    }
    ```

!!! info "¿Por qué `org.jetbrains.androidx.lifecycle`?"
    La librería de ViewModel de Google es solo para Android. JetBrains publica una **versión multiplataforma** con los **mismos paquetes**: en el código sigues escribiendo `import androidx.lifecycle.ViewModel` y `import androidx.lifecycle.viewModelScope`. Lo único que cambia es la dependencia de Gradle.

## 3. Paso 1: el dominio y los datos

Copia los paquetes `juegos/domain` y `juegos/data` del proyecto de 3C a `shared/src/commonMain/kotlin/com/dam/misjuegos/`, manteniendo la estructura de carpetas:

```text
shared/src/commonMain/kotlin/com/dam/misjuegos/
└── juegos/
    ├── domain/
    │   ├── Juego.kt
    │   ├── JuegoRepositorio.kt
    │   └── usecase/
    │       ├── ObtenerJuegosUseCase.kt
    │       ├── ObservarJuegoUseCase.kt
    │       └── AlternarFavoritoUseCase.kt
    └── data/
        └── JuegoRepositorioEnMemoria.kt
```

Solo hay que **cambiar la línea `package`** si el paquete base del proyecto nuevo es distinto. El resto compila tal cual: el dominio es Kotlin puro y solo usa `kotlinx.coroutines`, que es multiplataforma.

!!! tip "La prueba de fuego de la arquitectura"
    Si al moverlo a `commonMain` algún fichero del dominio da error, es que **tenía algo de Android** (o de Java) que no debía estar ahí. KMP es un buen detector de capas mal separadas.

## 5. Paso 3: Koin en el código común

Los módulos de 3C.3 también se mueven a `commonMain`. Solo hay que separar lo que depende de la plataforma, como `androidContext()`, que únicamente existe en Android:

```kotlin
// shared/src/commonMain/kotlin/com/dam/misjuegos/di/Koin.kt
val datosModule = module {
    singleOf(::JuegoRepositorioEnMemoria) bind JuegoRepositorio::class
}

val dominioModule = module {
    factoryOf(::ObtenerJuegosUseCase)
    factoryOf(::ObservarJuegoUseCase)
    factoryOf(::AlternarFavoritoUseCase)
}

val presentacionModule = module {
    viewModelOf(::CatalogoViewModel)
    viewModelOf(::DetalleViewModel)
}

/** Arranca Koin. Cada plataforma puede añadir su configuración con [config]. */
fun initKoin(config: KoinAppDeclaration = {}) {
    startKoin {
        config()
        modules(datosModule, dominioModule, presentacionModule)
    }
}
```

Y cada app lo arranca desde su punto de entrada, como en el reto avanzado de 3D.1:

=== "androidApp: MisJuegosApp.kt"

    ```kotlin
    class MisJuegosApp : Application() {
        override fun onCreate() {
            super.onCreate()
            initKoin {
                androidLogger()
                androidContext(this@MisJuegosApp)
            }
        }
    }
    ```

=== "desktopApp: main.kt"

    ```kotlin
    fun main() {
        initKoin()
        application {
            Window(onCloseRequest = ::exitApplication, title = "Mis juegos") {
                App()
            }
        }
    }
    ```

### Las pantallas, de momento, siguen en Android

Hasta 3D.3, las pantallas de Jetpack Compose de 3C se quedan en el módulo `androidApp`. Siguen funcionando igual: obtienen los ViewModel con `koinViewModel()`, solo que ahora esos ViewModel vienen de `shared`. Para que `androidApp` pueda usar Navigation 3 y los decoradores de 3B.1, añade allí esas dependencias, igual que en el proyecto de 3C.

Esta situación intermedia (lógica compartida e interfaz propia de cada plataforma) es, de hecho, una forma válida de usar KMP: es la que eligen muchas empresas que quieren conservar una interfaz nativa en iOS con SwiftUI.

## 6. Lo que cada plataforma hace a su manera

Hasta aquí todo era común. Pero hay cosas que **cada plataforma resuelve de forma distinta**. Por ejemplo, queremos un botón «Compartir» en el detalle de un juego:

- En **Android**, se abre el menú del sistema para compartir con otras apps (un `Intent`).
- En **escritorio**, no existe ese menú: copiaremos el texto al portapapeles.

KMP ofrece dos herramientas para estos casos.

### 6.1. Opción A: `expect` / `actual`

La vimos en 3D.1: se declara una función (o clase) en `commonMain` con `expect` y cada plataforma la implementa con `actual`. Es perfecta para cosas **pequeñas y sin dependencias**:

```kotlin
// commonMain
expect fun nombrePlataforma(): String

// androidMain
actual fun nombrePlataforma(): String = "Android"

// jvmMain
actual fun nombrePlataforma(): String = "Escritorio"
```

El problema aparece cuando la implementación **necesita algo**. Para lanzar un `Intent` en Android hace falta un `Context`, que una función `expect` no puede recibir sin ensuciar el código común. Además, no se puede sustituir por un *fake* en los tests.

### 6.2. Opción B: una interfaz con una implementación por plataforma (recomendada)

Es lo mismo que hicimos con `JuegoRepositorio` en 3C.2, ahora aplicado a la plataforma: el código común define **qué necesita** con una interfaz, y cada plataforma aporta **su implementación** a través de Koin.

**1. La interfaz, en `commonMain`:**

```kotlin
// shared/src/commonMain/kotlin/com/dam/misjuegos/plataforma/Compartidor.kt
interface Compartidor {
    fun compartir(texto: String)
}
```

**2. Una implementación en cada plataforma:**

=== "androidMain"

    ```kotlin
    // shared/src/androidMain/kotlin/com/dam/misjuegos/plataforma/CompartidorAndroid.kt
    class CompartidorAndroid(private val context: Context) : Compartidor {
        override fun compartir(texto: String) {
            val intent = Intent(Intent.ACTION_SEND).apply {
                type = "text/plain"
                putExtra(Intent.EXTRA_TEXT, texto)
            }
            val selector = Intent.createChooser(intent, null).apply {
                addFlags(Intent.FLAG_ACTIVITY_NEW_TASK)   // necesario al lanzar desde el contexto de la app
            }
            context.startActivity(selector)
        }
    }
    ```

=== "jvmMain"

    ```kotlin
    // shared/src/jvmMain/kotlin/com/dam/misjuegos/plataforma/CompartidorEscritorio.kt
    import java.awt.Toolkit
    import java.awt.datatransfer.StringSelection

    class CompartidorEscritorio : Compartidor {
        override fun compartir(texto: String) {
            Toolkit.getDefaultToolkit().systemClipboard.setContents(StringSelection(texto), null)
        }
    }
    ```

**3. Un módulo de Koin por plataforma.** Aquí sí es útil `expect`/`actual`, para que el código común sepa que «cada plataforma tiene su módulo»:

=== "commonMain"

    ```kotlin
    expect val plataformaModule: Module
    ```

=== "androidMain"

    ```kotlin
    actual val plataformaModule: Module = module {
        single<Compartidor> { CompartidorAndroid(androidContext()) }
    }
    ```

=== "jvmMain"

    ```kotlin
    actual val plataformaModule: Module = module {
        single<Compartidor> { CompartidorEscritorio() }
    }
    ```

Y se añade a `initKoin`:

```kotlin
fun initKoin(config: KoinAppDeclaration = {}) {
    startKoin {
        config()
        modules(datosModule, dominioModule, presentacionModule, plataformaModule)
    }
}
```

**4. El caso de uso, común, usa la interfaz sin saber cómo se implementa:**

```kotlin
class CompartirJuegoUseCase(private val compartidor: Compartidor) {
    // Regla común: el formato del texto es el mismo en todas las plataformas
    operator fun invoke(juego: Juego) {
        compartidor.compartir("🎮 Te recomiendo «${juego.titulo}» (${juego.plataforma})")
    }
}
```

Fíjate en el reparto: **qué** se comparte (el texto) es una regla de la app y está en el código común; **cómo** se comparte depende de la plataforma y está en `androidMain` o `jvmMain`.

### 6.3. ¿Cuál elijo?

| Situación | Herramienta |
|---|---|
| Un valor o una función pequeña sin dependencias (nombre de la plataforma, separador de rutas…) | `expect` / `actual` |
| La implementación necesita objetos de la plataforma (`Context`, ventana, ficheros…) | Interfaz + Koin |
| Quieres poder sustituirla por un *fake* en los tests | Interfaz + Koin |
| Declarar el módulo de Koin de cada plataforma | `expect val …: Module` |

La recomendación general es **preferir interfaces inyectadas** y reservar `expect`/`actual` para piezas pequeñas.

## 7. Tests en `commonTest`

Los tests de 3C.4 también se pueden compartir: en `shared/src/commonTest` se ejecutan **para todas las plataformas**. Hay que hacer tres cambios, porque JUnit solo existe en la JVM:

| En `src/test` (Android, 3C.4) | En `commonTest` (KMP) |
|---|---|
| `import org.junit.Test` | `import kotlin.test.Test` |
| `org.junit.Assert.assertEquals` | `kotlin.test.assertEquals` |
| `@get:Rule val mainDispatcherRule = MainDispatcherRule()` | `@BeforeTest` con `Dispatchers.setMain(…)` y `@AfterTest` con `Dispatchers.resetMain()` |

`kotlinx-coroutines-test` y Turbine ya son multiplataforma, así que `runTest`, `backgroundScope` y `test { awaitItem() }` funcionan igual.

```kotlin
// shared/src/commonTest/kotlin/com/dam/misjuegos/juegos/CatalogoViewModelTest.kt
import kotlin.test.AfterTest
import kotlin.test.BeforeTest
import kotlin.test.Test
import kotlin.test.assertEquals
import kotlin.test.assertIs

class CatalogoViewModelTest {

    @BeforeTest
    fun setUp() = Dispatchers.setMain(UnconfinedTestDispatcher())

    @AfterTest
    fun tearDown() = Dispatchers.resetMain()

    @Test
    fun con_datos_el_estado_pasa_a_exito() = runTest {
        val repositorio = FakeJuegoRepositorio(listOf(Juego(1, "Hades", "PC")))
        val viewModel = CatalogoViewModel(
            ObtenerJuegosUseCase(repositorio),
            AlternarFavoritoUseCase(repositorio)
        )
        backgroundScope.launch(UnconfinedTestDispatcher(testScheduler)) { viewModel.uiState.collect {} }

        val estado = assertIs<CatalogoUiState.Exito>(viewModel.uiState.value)
        assertEquals("Hades", estado.juegos.single().titulo)
    }
}
```

!!! note "Nombres de test sin espacios"
    En `commonTest` es mejor usar nombres de función sin espacios ni comillas invertidas (`con_datos_el_estado_pasa_a_exito`). Los nombres con espacios funcionan en la JVM, pero no en todas las plataformas de KMP.

Para ejecutarlos:

```bash
./gradlew :shared:jvmTest
```

```bash
./gradlew :shared:allTests
```

`jvmTest` ejecuta los tests comunes en la JVM y es lo más rápido para el día a día. `allTests` los ejecuta para todas las plataformas configuradas.

El test de Koin con `verify()` ([3C.3](../c-arquitectura/3c.3-inyeccion-dependencias-koin.md#8-comprobar-los-modulos-con-un-test)) solo funciona en la JVM, así que va en `shared/src/jvmTest`.

## 8. Errores frecuentes

!!! warning "`Unresolved reference: Log` (u otra clase de Android) en `commonMain`"
    Algún ViewModel o repositorio usaba `android.util.Log`, `Context` o similares. Sácalo del código común: usa una interfaz inyectada (apartado 6) o, para registrar mensajes, una librería multiplataforma de *logging*.

!!! warning "`java.util.UUID`, `java.time.LocalDate` o `java.io.File` no existen en `commonMain`"
    Son clases de Java, que solo existe en Android y escritorio. Usa sus alternativas multiplataforma: `kotlin.uuid.Uuid` para identificadores, la librería `kotlinx-datetime` para fechas y una interfaz por plataforma para ficheros.

!!! warning "La app de escritorio falla con «Module with the Main dispatcher is missing»"
    Falta `kotlinx-coroutines-swing` en `desktopApp`. Sin ella, `viewModelScope` no tiene hilo principal en escritorio.

!!! warning "`androidContext()` no se encuentra en `commonMain`"
    Es de `koin-android` y solo existe en Android. Úsalo en `androidMain` (en el `plataformaModule`) o en el módulo `androidApp`.

!!! warning "Los tests de `commonTest` no compilan: no encuentra `org.junit`"
    En el código común no hay JUnit. Cambia los imports a `kotlin.test` y sustituye la `MainDispatcherRule` por `@BeforeTest`/`@AfterTest` (apartado 7).

!!! warning "`actual` sin su `expect` (o al revés)"
    El `expect` y todos sus `actual` deben estar en el **mismo paquete** y tener exactamente la misma firma. Si falta el `actual` de una plataforma, el compilador lo indica.

## 9. Retos

### 🟢 Básico: los tests a `commonTest`

Mueve a `shared/src/commonTest` el `FakeJuegoRepositorio` y los tests de `ObtenerJuegosUseCase` de 3C.4, haz los cambios necesarios y ejecútalos con `./gradlew :shared:jvmTest`.

??? success "Solución"

    ```kotlin
    // shared/src/commonTest/kotlin/com/dam/misjuegos/juegos/ObtenerJuegosUseCaseTest.kt
    import kotlin.test.Test
    import kotlin.test.assertEquals
    import kotlin.test.assertTrue

    class ObtenerJuegosUseCaseTest {

        private val hades = Juego(1, "Hades", "PC")
        private val celeste = Juego(2, "Celeste", "PC")
        private val zelda = Juego(3, "Zelda", "Switch", esFavorito = true)

        @Test
        fun devuelve_favoritos_primero_y_el_resto_alfabeticamente() = runTest {
            val obtenerJuegos = ObtenerJuegosUseCase(FakeJuegoRepositorio(listOf(hades, celeste, zelda)))

            assertEquals(listOf(zelda, celeste, hades), obtenerJuegos().first())
        }

        @Test
        fun con_repositorio_vacio_devuelve_lista_vacia() = runTest {
            val obtenerJuegos = ObtenerJuegosUseCase(FakeJuegoRepositorio())

            assertTrue(obtenerJuegos().first().isEmpty())
        }
    }
    ```

    Claves de la solución:

    - El `FakeJuegoRepositorio` se mueve **sin cambios**: solo usa Kotlin y `kotlinx.coroutines`.
    - Los únicos cambios son los imports (`kotlin.test` en lugar de `org.junit`) y los nombres sin espacios.
    - Estos tests protegen ahora la lógica de **todas** las plataformas a la vez.

### 🟡 Intermedio: registrar mensajes en cada plataforma

Crea con `expect`/`actual` una función `registrar(mensaje: String)` que en Android escriba en Logcat (`Log.d("MisJuegos", …)`) y en escritorio en la consola (`println`). Úsala en `JuegoRepositorioEnMemoria.alternarFavorito` para registrar cada cambio y comprueba los mensajes en las dos apps.

??? success "Solución"

    ```kotlin
    // commonMain: com/dam/misjuegos/plataforma/Registro.kt
    expect fun registrar(mensaje: String)

    // androidMain: com/dam/misjuegos/plataforma/Registro.android.kt
    actual fun registrar(mensaje: String) {
        android.util.Log.d("MisJuegos", mensaje)
    }

    // jvmMain: com/dam/misjuegos/plataforma/Registro.jvm.kt
    actual fun registrar(mensaje: String) {
        println("[MisJuegos] $mensaje")
    }

    // commonMain: JuegoRepositorioEnMemoria.kt
    override suspend fun alternarFavorito(id: Int) {
        juegos.update { lista ->
            lista.map { juego ->
                if (juego.id == id) {
                    juego.copy(esFavorito = !juego.esFavorito)
                        .also { registrar("Favorito de «${it.titulo}»: ${it.esFavorito}") }
                } else juego
            }
        }
    }
    ```

    Claves de la solución:

    - Es un buen caso para `expect`/`actual`: una función pequeña, **sin dependencias** y que no hace falta sustituir en los tests.
    - `android.util.Log` solo aparece en `androidMain`; el repositorio sigue siendo código común.
    - En Android, filtra Logcat por la etiqueta `MisJuegos`; en escritorio, los mensajes salen en la consola de ejecución del IDE.

### 🔴 Avanzado: compartir un juego, con test

Implementa la funcionalidad de compartir del apartado 6 (interfaz `Compartidor`, implementaciones de Android y escritorio, `plataformaModule` y `CompartirJuegoUseCase`). Añade al `DetalleViewModel` una función `onCompartirClick()`. Escribe en `commonTest` un test que compruebe el texto que se comparte usando un *fake* de `Compartidor`.

??? success "Solución"

    ```kotlin
    // commonMain: DetalleViewModel.kt (cambios)
    class DetalleViewModel(
        private val juegoId: Int,
        observarJuego: ObservarJuegoUseCase,
        private val alternarFavorito: AlternarFavoritoUseCase,
        private val compartirJuego: CompartirJuegoUseCase
    ) : ViewModel() {

        val uiState: StateFlow<DetalleUiState> = /* … igual que en 3C.2 … */

        fun onCompartirClick() {
            uiState.value.juego?.let { compartirJuego(it) }
        }
    }

    // commonMain: Koin.kt (cambios)
    val dominioModule = module {
        // …
        factoryOf(::CompartirJuegoUseCase)
    }

    // commonTest: CompartirJuegoUseCaseTest.kt
    class CompartidorFake : Compartidor {
        val compartidos = mutableListOf<String>()
        override fun compartir(texto: String) {
            compartidos += texto
        }
    }

    class CompartirJuegoUseCaseTest {

        @Test
        fun comparte_el_titulo_y_la_plataforma() {
            val compartidor = CompartidorFake()
            val compartirJuego = CompartirJuegoUseCase(compartidor)

            compartirJuego(Juego(7, "Zelda", "Switch"))

            assertEquals(listOf("🎮 Te recomiendo «Zelda» (Switch)"), compartidor.compartidos)
        }
    }
    ```

    Claves de la solución:

    - La interfaz `Compartidor` permite probar el caso de uso con un **fake** que solo guarda lo que recibe. Con `expect`/`actual` no se podría: el test ejecutaría la implementación real.
    - `CompartidorAndroid` recibe el `Context` desde Koin (`androidContext()`) y el código común nunca lo ve.
    - `DetalleViewModel` recibe un parámetro más; como se declara con `viewModelOf(::DetalleViewModel)`, Koin lo resuelve solo. El `juegoId` sigue llegando con `parametersOf`.
    - El test de `verify()` en `jvmTest` detectaría si olvidas registrar `CompartirJuegoUseCase` o el `Compartidor` del módulo de plataforma. Como `plataformaModule` es distinto en cada plataforma, en `jvmTest` se verifica con la implementación de escritorio.
