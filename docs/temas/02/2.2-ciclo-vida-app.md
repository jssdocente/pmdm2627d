# **2.2 Ciclo de vida de una aplicación Android moderna**

A diferencia de un programa de consola o una aplicación de escritorio tradicional que cuenta con un único punto de entrada `main()` predecible, una aplicación Android está sujeta al control dinámico del sistema operativo. Android puede pausar, detener o destruir componentes de nuestra aplicación en cualquier momento para liberar memoria RAM o gestionar llamadas entrantes.

Comprender el ciclo de vida de una **Activity** y cómo interactúa con el árbol de componibles de **Jetpack Compose** es indispensable para evitar fugas de memoria y pérdidas accidentales de datos del usuario.

---

## 1. La Activity en el Ecosistema Moderno

Una **Activity** representa una única ventana o superficie gráfica donde el usuario interactúa con la aplicación. En el paradigma tradicional basado en XML se utilizaban múltiples Activities o Fragmentos para navegar entre pantallas. 

En la arquitectura moderna recomendada por Google, se adopta el patrón **Single-Activity Architecture**: la aplicación cuenta con una única Activity principal (`MainActivity`), y toda la navegación e interfaces se gestionan como funciones componibles declarativas de Compose.

### Proceso, `Application` y `Activity`: quién es quién

Al hablar de «la app» se mezclan tres piezas distintas. Conviene separarlas antes de estudiar el ciclo de vida, porque cada una vive un tiempo diferente:

<figure class="arq-fig">
--8<-- "docs/temas/02/images/arranque/app-piezas.svg"
<figcaption>El proceso contiene un objeto <code>Application</code> y la <code>MainActivity</code>. Dentro de la Activity, <code>setContent</code> dibuja el tema de Compose y la función composable raíz.</figcaption>
</figure>

| Pieza | Qué es | ¿Hace falta? | Cuánto vive |
|---|---|---|---|
| **Proceso** | El programa en ejecución. Lo crea Android al abrir la app. | Lo gestiona el sistema. | Hasta que el sistema lo cierra para liberar memoria, aunque la app no esté a la vista. |
| **`Application`** | Un **objeto** que Android crea una sola vez por proceso, antes que cualquier Activity. | No. Si no creas una propia, Android usa una genérica. | Lo mismo que el proceso. |
| **`MainActivity`** | Una **ventana**: el punto de entrada que abre el lanzador. | Sí, al menos una. | Menos: se destruye y se vuelve a crear, por ejemplo, al girar la pantalla. |
| **`LabApp()`** | Una **función `@Composable`** raíz con toda la interfaz. El nombre es una convención: en otros proyectos verás `App()` o `GameVaultApp()`. | No es obligatoria, pero ordena el código. | Se ejecuta (y se recompone) mientras la Activity muestra su contenido. |

!!! warning "`Application` no envuelve a la Activity"

    No son una «caja» dentro de otra: las dos viven en el mismo proceso. `Application` solo garantiza que su `onCreate()` se ejecuta **una vez y antes** que el de cualquier Activity. Por eso, cuando más adelante necesites arrancar algo global (la inyección de dependencias con Koin, Firebase…), crearás tu propia clase y la registrarás en el Manifest:

    ```kotlin
    class LabApplication : Application() {
        override fun onCreate() {
            super.onCreate()
            // Se ejecuta una vez por proceso, antes que cualquier Activity
        }
    }
    ```

    ```xml
    <application
        android:name=".LabApplication"
        ... >
    ```

    Sin `android:name`, Android no la usa. Ojo con los nombres: la **etiqueta** `<application>` del Manifest existe siempre (agrupa el icono, el nombre y el tema de toda la app); la **clase** `Application` propia solo existe si la creas tú.

### De `AppCompatActivity` a `ComponentActivity`

Históricamente, las aplicaciones Android heredaban de `AppCompatActivity` para dar soporte a temas antiguos y a la ActionBar. En Compose moderno se hereda directamente de **`ComponentActivity`**, la cual proporciona soporte nativo para `setContent { ... }` y los componentes de arquitectura modernos:

=== "Moderno (Jetpack Compose)"

    ```kotlin
    package com.pmdm.lab.ut2

    import android.os.Bundle
    import androidx.activity.ComponentActivity
    import androidx.activity.compose.setContent
    import com.pmdm.lab.ut2.ui.theme.LabUt2Theme

    class MainActivity : ComponentActivity() {
        override fun onCreate(savedInstanceState: Bundle?) {
            super.onCreate(savedInstanceState)
            // setContent enlaza directamente el árbol de Compose a la Activity
            setContent {
                LabUt2Theme {
                    LabApp() // Composable raíz de la app
                }
            }
        }
    }
    ```

=== "Histórico / Obsoleto (XML Views)"

    ```kotlin
    // NO UTILIZAR: Patrón imperativo antiguo
    class MainActivity : AppCompatActivity() {
        override fun onCreate(savedInstanceState: Bundle?) {
            super.onCreate(savedInstanceState)
            setContentView(R.layout.activity_main) // Inflaba un layout XML
            val miBoton = findViewById<Button>(R.id.miBoton) // Búsqueda manual de vistas
        }
    }
    ```

### Qué pasa al pulsar el icono

Juntando las piezas, este es el orden en que se ponen en marcha cuando el usuario abre la app:

<figure class="arq-fig">
--8<-- "docs/temas/02/images/arranque/app-arranque.svg"
<figcaption>Arranque en frío. Hasta que Compose pinta el primer fotograma, el usuario ve una ventana que el sistema dibuja con el tema XML de la app.</figcaption>
</figure>

Dos detalles de esta secuencia que aparecerán más adelante:

- **Lo primero que se ve no es tu código.** Mientras se crea el proceso, Android ya muestra una ventana dibujada con el **tema XML** de la app (el `android:theme` del Manifest, explicado en [2.1 §3.3](./2.1-primeros-pasos.md#33-el-tema-xml-de-la-ventana)). Desde Android 12 esa ventana es la **pantalla de inicio** con el icono de la app; cómo personalizarla está en el [Anexo B](../00-android/anexos/b-pantalla-inicio-splash.md).
- **El proceso puede morir con la app en segundo plano.** Si el sistema necesita memoria, cierra el proceso entero, `Application` incluida. Al volver, Android lo crea de nuevo y recrea la Activity desde cero: lo que estaba solo en memoria se pierde. Es el motivo de `rememberSaveable` ([§4.2](#42-remember-vs-remembersaveable)).

## 2. Estados y Métodos del Ciclo de Vida de la Activity

Una Activity transita por una máquina de estados gestionada por el sistema operativo:

<figure class="arq-fig">
--8<-- "docs/temas/02/images/ciclo/cv-estados.svg"
<figcaption>Cada escalón es un estado y cada flecha, el método que Android llama al pasar de uno a otro. Fíjate en la flecha discontinua: si el sistema elimina el proceso, <code>onDestroy()</code> no llega a ejecutarse.</figcaption>
</figure>

### Descripción de los Métodos del Ciclo de Vida

- **`onCreate()`:** Se ejecuta una sola vez cuando la Activity se instancia en memoria. Aquí se configura la interfaz con `setContent { ... }` y se inicializan recursos estáticos.
- **`onStart()`:** La Activity se vuelve visible en pantalla para el usuario, aunque todavía no tiene el foco para interactuar con ella.
- **`onResume()`:** La Activity pasa a primer plano (*foreground*) y adquiere el foco interactivo completo. Es el momento idóneo para reanudar animaciones o la captura de sensores.
- **`onPause()`:** La Activity pierde el foco interactivo parcial (por ejemplo, al abrir el menú de aplicaciones recientes o aparecer un diálogo modal del sistema). Debe pausar operaciones que consuman CPU intensiva.
- **`onStop()`:** La Activity deja de ser completamente visible porque el usuario ha pulsado el botón *Home* o ha cambiado de aplicación.
- **`onRestart()`:** Se ejecuta justo antes de `onStart()` cuando la Activity vuelve de estar parada (por ejemplo, al regresar a la app tras pulsar *Home*).
- **`onDestroy()`:** Se invoca antes de que la Activity sea destruida por completo: porque el usuario pulsó *Atrás* para salir, porque se llamó a `finish()` o porque hay un cambio de configuración, como girar la pantalla.

!!! warning "`onDestroy()` no está garantizado"
    Si el sistema necesita memoria mientras la app está en segundo plano, puede **eliminar el proceso entero** sin llamar a `onDestroy()`. Por eso nunca se deja para `onDestroy()` algo imprescindible, como guardar los datos del usuario.

## 3. Depuración del Ciclo de Vida con Logcat

Para inspeccionar la ejecución de nuestra aplicación en tiempo real utilizamos la clase `android.util.Log` y la herramienta **Logcat** integrada en IntelliJ IDEA (pestaña inferior *Logcat*):

```kotlin
import android.util.Log

class MainActivity : ComponentActivity() {

    companion object {
        private const val TAG = "CicloVidaLab"
    }

    override fun onCreate(savedInstanceState: Bundle?) {
        super.onCreate(savedInstanceState)
        Log.d(TAG, "onCreate: Activity creada")
    }

    override fun onStart() {
        super.onStart()
        Log.d(TAG, "onStart: Activity visible")
    }

    override fun onResume() {
        super.onResume()
        Log.d(TAG, "onResume: Activity en primer plano con foco")
    }

    override fun onPause() {
        super.onPause()
        Log.d(TAG, "onPause: Activity perdiendo el foco")
    }

    override fun onStop() {
        super.onStop()
        Log.d(TAG, "onStop: Activity en segundo plano (no visible)")
    }

    override fun onDestroy() {
        super.onDestroy()
        Log.d(TAG, "onDestroy: Activity destruida")
    }
}
```

!!! tip "Filtrar mensajes en Logcat"

    En la pestaña inferior **Logcat** de IntelliJ IDEA, escribe en la barra de búsqueda: `tag:CicloVidaLab`. Esto ocultará los miles de mensajes internos del sistema operativo y mostrará exclusivamente los logs de tu aplicación.

## 4. El Ciclo de Vida desde la Perspectiva de Jetpack Compose

En Compose existen dos conceptos cruciales que cambian radicalmente la forma de pensar sobre el ciclo de vida:

### 4.1. Recomposición vs Ciclo de Vida del Sistema

- **Recomposición:** Es el proceso interno mediante el cual Compose vuelve a ejecutar únicamente las funciones `@Composable` que leen un estado que ha cambiado. La Activity **no se reinicia ni se destruye**. Es una operación ligera y reactiva en memoria.
- **Cambio de Configuración (Rotación de Pantalla):** Cuando el usuario gira el teléfono entre orientación vertical y horizontal, el sistema operativo Android **destruye y recrea la Activity por completo** (`onPause` -> `onStop` -> `onDestroy` -> `onCreate`).
- **Eliminación del proceso:** Con la app en segundo plano, el sistema puede cerrar el proceso para liberar memoria. Cuando el usuario vuelve, Android crea un proceso y una Activity nuevos ([§1](#que-pasa-al-pulsar-el-icono)).

<figure class="arq-fig">
--8<-- "docs/temas/02/images/ciclo/cv-que-sobrevive.svg"
<figcaption>Qué estado sobrevive a cada situación. La recomposición no toca la Activity; el giro la recrea; la eliminación del proceso lo recrea todo.</figcaption>
</figure>

### 4.2. `remember` vs `rememberSaveable`

Este es el primer gran reto que afrontan los desarrolladores noveles en Compose:

- **`remember { mutableStateOf(...) }`:** Conserva el valor únicamente durante las **recomposiciones** normales de la pantalla. Si el usuario rota el dispositivo, la Activity se destruye y el valor vuelve a su estado inicial por defecto.
- **`rememberSaveable { mutableStateOf(...) }`:** Guarda automáticamente el valor en el `Bundle` de estado guardado de Android. Cuando la Activity se destruye por rotación o por presión de memoria del sistema, el valor **se recupera y sobrevive de forma transparente**.

```kotlin
// Este valor volverá a 0 si el usuario gira el dispositivo
var contadorVolatil by remember { mutableIntStateOf(0) }

// Este valor conservará la cuenta intacta incluso al rotar la pantalla
var contadorPersistente by rememberSaveable { mutableIntStateOf(0) }
```
